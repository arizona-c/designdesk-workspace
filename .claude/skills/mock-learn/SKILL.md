モックアップ作成の「学習」を行う。学習＝モデルを鍛えることではなく、案件ごとの知識の正本（Web「モックアップ作成」）を育てること。**候補を出すのは AI、採用は人**。

## 手順

1. `mock_get_knowledge`（include_candidates: true）で、採用済みの知識と未採用の候補を読む。同じテーマを重ねて提案しない。
2. `mock_get_samples` で取り出し結果を読む。無ければ作業者に「Figma プラグインで手本にする画面を選び、設定 → モックアップ作成 → 取り出す」を頼んで待つ。AI は取り出しをしない。
3. 取り出し結果を横断して、繰り返し現れているものだけを候補にする。1候補=1テーマ:
   - `layout`（画面の型）: 「一覧画面はヘッダー → 絞り込み → カード一覧（2列）→ 右下に主ボタン」のように、区画の並びと役割
   - `component_usage`（部品の使い方）: どの部品をどの場面でどのバリアントで使うか（部品名とキーを data に残す）
   - `spacing`（余白と幅）: 使われている刻み（例: 8 / 16 / 24）と画面幅
   - `typography`（文字）: 見出し・本文・補足のサイズと太さ
   - `color`（色）: 役割ごとの色（変数名があればそれ）
   - `copy`（文言）: ボタンや見出しの言い回しの型
4. 見出しは平易な日本語、本文は **次にモックを描く AI がそのまま従える具体さ**（数値・部品名・並び順）で書き、`mock_propose_pattern` で1件ずつ提案する（source は省略＝ai、source_ref に元の Frame の node_id）。
5. 終わったら `mock_record_run`（kind: "learn"・count: 提案数）で記録し、作業者に「Web の モックアップ作成 → 知識 で候補を読み、採用・却下してください。本文はその場で直せます」と案内する。

## してはいけないこと

- 汎用的なデザインの常識を候補にしない（この案件では「それらしさ」を阻害するノイズになる）。手本に実際に現れているものだけ
- 1件に複数テーマを詰めない。既にある知識と重複する候補を出さない
- 採用状態を変えようとしない（人の仕事）
