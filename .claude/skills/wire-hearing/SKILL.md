ワイヤー生成（案件の「画面と遷移」の正本づくり）のヒアリングを進める。描くのはこのスキルの仕事ではない（作業者が Figma プラグインの「設定 → ワイヤー生成 → 描く」で行う）。

## 手順

1. `wire_get_rules` を呼び、返ってきた **rules（案件のルール文）に従う**。ルール文は案件ごとに人が編集した正本で、ここに書かれた「画面のまとめ方・遷移の決め方・ヒアリングの進め方」が最優先。
2. 棚卸しが無ければ（counts.inventories が 0）、作業者に「Figma プラグインを開き、設定 → ワイヤー生成 → 棚卸しを実行」を頼んで待つ。AI は棚卸しをしない。
3. `wire_get_inventory` で仮グループ（Frame 名の前半でまとめたもの）と `wire_list_screens` で決まっている画面を読む。`assigned_to` の付いた Frame は済み。
4. ヒアリングは **一度に3問まで**。仮グループごとに「この Frame 群は同じ画面の状態違いでよいか」「画面名はこれでよいか（画面一覧の呼称があればそれ）」「行き先はどこか（links_to を候補として示す）」を具体的に聞く。長くなってよい。完璧を目指して止まらない。
5. 決まった画面から順に `wire_upsert_screen`（states に Frame 群・registry_name に画面一覧の呼称）、遷移は `wire_upsert_transition`（条件があれば短いラベル）で書く。**書く前に作業者の同意を得る**。あとで Web の「ワイヤー生成」で直せることを伝える。
6. まだ Frame の無い画面（画面ゼロから始める場合）は、作業者と区画の並び（ヘッダー・ナビ・一覧・フォーム・文章・画像・主ボタン・フッター）を決め、`layout: { source: "kit", regions: [...] }` で登録する。
7. 一区切りごとに「決まった画面 N 件・遷移 M 件・残り」を短く伝える。全部終わったら「プラグインの 設定 → ワイヤー生成 → 描く準備 で内容を確認して描いてください。2回目以降は前回との差分の強調を提案されます」と案内する。

## してはいけないこと

- 作業者に確認せずに画面や遷移を確定・削除しない
- 同じ画面内の開閉（アコーディオン・ポップアップ）を遷移として登録しない（画面の状態として states に入れる）
- 略号・内部名の画面名を付けない（利用者の言葉・画面一覧の呼称に揃える）
- Figma のノードを変更しない（読むだけ）
